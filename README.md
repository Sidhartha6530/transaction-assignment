# Toucan Payments - Transaction Processing Service

Engineering challenge submission for the 2026 Fresher Engineering Trainee Programme.

---

## 1. Understanding of the Problem

This project implements a Spring Boot REST API for creating and managing customer financial transactions. The service is designed to validate transaction data, generate unique identifiers, store transactions, and enforce a controlled transaction lifecycle.

The implemented service supports:

1. **Creating transactions** with validation for customer ID, amount, currency, and transaction type.
2. **Retrieving transactions** by ID with `404 Not Found` handling.
3. **Updating transaction status** using explicit lifecycle rules.
4. **Retrieving transactions for a customer** using a normalized numeric customer ID.
5. **Retrieving all stored transactions**.

---

## 2. Assumptions Made

- **Monetary precision**: Amounts use `BigDecimal` and may have no more than 2 decimal places.
- **Transaction IDs**: IDs are generated by the service in the format `TP` followed by 10 digits. Clients do not provide the ID when creating a transaction.
- **Customer IDs**: Customer IDs are numeric and normalized to an 8-digit value. For example, `1` is stored as `00000001`.
- **Initial status**: New transactions start in `PENDING`. A transaction cannot be created directly in a terminal status.
- **Terminal states**: `COMPLETED`, `FAILED`, and `CANCELLED` are terminal states.
- **Currency**: Currency must be a three-letter uppercase ISO-4217 code validated with `java.util.Currency`.
- **Persistence**: Transactions are stored in an in-memory H2 database and are lost when the application stops.

## 3. Validation Rules & State Machine

### Field Validations

| Field | Type | Rules | Error Response |
|---|---|---|---|
| `transactionId` | String | Generated by the service in the format `TP[0-9]{10}`. | `400 Bad Request` for an invalid ID |
| `customerId` | String | Required numeric value with 1 to 8 digits; normalized to 8 digits and limited to `00000001` through `99999998`. | `400 Bad Request` |
| `amount` | BigDecimal | Required, from `0.01` to `9999999999.99`, with no more than 2 decimal places. | `400 Bad Request` |
| `currency` | String | Required, exactly 3 uppercase letters and a valid ISO-4217 code. | `400 Bad Request` |
| `transactionType` | Enum | Required. Allowed values: `DEPOSIT`, `WITHDRAWAL`, `TRANSFER`, or `PAYMENT`. | `400 Bad Request` |
| `transactionStatus` | Enum | Defaults to `PENDING`. Any non-pending status supplied during creation is rejected. | `400 Bad Request` |

### Status Transition Rules

```text
                  +--------------> COMPLETED (Terminal)
                  |
  [PENDING] ------+--------------> FAILED    (Terminal)
                  |
                  +--------------> CANCELLED (Terminal)
```

- `PENDING` -> `COMPLETED`, `FAILED`, or `CANCELLED`.
- A terminal transaction cannot change status.
- Updating a transaction to its current status is rejected.
- Illegal status changes return `409 Conflict`.

## 4. API Endpoints

Base URL: `http://localhost:8080`

### A. Create Transaction

- **Endpoint**: `POST /api/transactions`
- **Request body**:

```json
{
  "customerId": "74125896",
  "amount": 150.75,
  "currency": "USD",
  "transactionType": "PAYMENT"
}
```

- **curl**:

```bash
curl -X POST http://localhost:8080/api/transactions \
  -H "Content-Type: application/json" \
  -d '{
    "customerId": "74125896",
    "amount": 150.75,
    "currency": "USD",
    "transactionType": "PAYMENT"
  }'
```

- **Response**: `201 Created` with the generated transaction ID and `PENDING` status.

```json
{
  "transactionId": "TP7412589638",
  "customerId": "74125896",
  "amount": 150.75,
  "currency": "USD",
  "transactionType": "PAYMENT",
  "transactionStatus": "PENDING",
  "createdAt": "2026-08-31T12:00:00",
  "updatedAt": null
}
```

### B. Get Transaction by ID

- **Endpoint**: `GET /api/transactions/{id}`
- **Example**: `GET /api/transactions/TP7412589638`
- **Responses**: `200 OK`, `400 Bad Request` for an invalid ID, or `404 Not Found` when the transaction does not exist.
- **curl**:

```bash
curl http://localhost:8080/api/transactions/TP7412589638
```

- **Response**: `200 OK` with the transaction object.

```json
{
  "transactionId": "TP7412589638",
  "customerId": "74125896",
  "amount": 150.75,
  "currency": "USD",
  "transactionType": "PAYMENT",
  "transactionStatus": "PENDING",
  "createdAt": "2026-08-31T12:00:00",
  "updatedAt": null
}
```

### C. Update Transaction Status

- **Endpoint**: `PUT /api/transactions/{id}/status?status={status}`
- **Example**: `PUT /api/transactions/TP1234567890/status?status=COMPLETED`
- **curl**:

```bash
curl -X PUT "http://localhost:8080/api/transactions/TP7412589638/status?status=COMPLETED"
```

- **Response**: `200 OK` with the updated transaction.
- **Invalid transition**: `409 Conflict`.

```json
{
  "transactionId": "TP7412589638",
  "customerId": "74125896",
  "amount": 150.75,
  "currency": "USD",
  "transactionType": "PAYMENT",
  "transactionStatus": "COMPLETED",
  "createdAt": "2026-08-31T12:00:00",
  "updatedAt": "2026-08-31T12:05:00"
}
```

### D. Get Customer Transactions

- **Endpoint**: `GET /api/transactions/customer/{customerId}`
- **Example**: `GET /api/transactions/customer/74125896`
- **curl**:

```bash
curl http://localhost:8080/api/transactions/customer/74125896
```

- **Response**: `200 OK` with the matching transactions.
- **Invalid customer ID**: `400 Bad Request`.

```json
[
  {
    "transactionId": "TP7412589638",
    "customerId": "74125896",
    "amount": 150.75,
    "currency": "USD",
    "transactionType": "PAYMENT",
    "transactionStatus": "PENDING",
    "createdAt": "2026-08-31T12:00:00",
    "updatedAt": null
  }
]
```

### E. Get All Transactions

- **Endpoint**: `GET /api/transactions`
- **curl**:

```bash
curl http://localhost:8080/api/transactions
```

- **Response**: `200 OK` with all transactions currently stored in H2.

```json
[
  {
    "transactionId": "TP7412589638",
    "customerId": "74125896",
    "amount": 150.75,
    "currency": "USD",
    "transactionType": "PAYMENT",
    "transactionStatus": "PENDING",
    "createdAt": "2026-08-31T12:00:00",
    "updatedAt": null
  }
]
```

## 5. How Testing Was Approached

The project uses Spring Boot integration tests with `TestRestTemplate` to exercise the real HTTP endpoints. The test suite contains 17 controller integration tests and 1 application-context test covering:

- Successful transaction creation and `201 Created` response.
- Automatic transaction ID generation and uniqueness.
- Customer ID normalization and preservation of leading zeroes.
- Transaction lookup and not-found handling.
- Customer transaction filtering and empty results.
- Invalid amount, currency, and customer ID rejection.
- Pending status enforcement during creation.
- Valid status updates from `PENDING`.
- Unchanged and terminal status transition conflicts.
- Helpful error message responses.
- Spring Boot application context loading.

---

## 6. Known Limitations

- H2 is an in-memory database, so data does not persist across application restarts.
- Transaction IDs cannot be supplied by clients and there is no separate idempotency-key mechanism.
- Currency updates are not implemented as a separate endpoint.
- Customer transactions are not explicitly sorted chronologically by the repository query.
- There is no pagination or advanced filtering.
- Authentication and authorization are not implemented.
- Error responses are plain text rather than a standardized error object.
- There is no audit history for status changes.

---

## 7. What Would Be Improved with More Time

- Replace the H2 in-memory database with a persistent production database and database migration scripts.
- Add authentication and authorization so customers can access only their own transactions.
- Add pagination, sorting, and filtering to transaction listing endpoints using Spring Data `Pageable`.
- Add structured error responses with machine-readable error codes and request details.
- Add idempotency keys and optimistic locking to prevent duplicate requests and concurrent update conflicts.
- Add audit history for transaction status changes and OpenAPI documentation with broader negative-test coverage.
